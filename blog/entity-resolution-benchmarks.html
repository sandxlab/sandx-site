Building a Production-Grade Entity Resolution Engine in Python

SandX Lab May 2026 9 min read

Every production data system eventually hits the same wall: the same real-world entity appears in multiple records under different names, with different spellings, or with missing fields. A customer is "Acme Corp" in one table and "ACME Corporation" in another. A research paper appears in both DBLP and ACM with slightly different author lists. Entity resolution (ER) is the problem of deciding which records refer to the same thing.

The naive approach — fuzzy string matching with a threshold — breaks down fast. At O(N²) candidate pairs, a 100,000-record dataset generates 5 billion comparisons. And a single threshold applied globally ignores the fact that "Smith" is a worse identifier than "Yannis Ioannidis".

We built sandx-er to solve this properly: a modular, composable Python pipeline that handles the full ER workflow — blocking, matching, and clustering — with every output carrying a probabilistic confidence score. This post covers the architecture and benchmark results on two standard datasets.

The Pipeline

Entity resolution decomposes into three stages. Blocking reduces O(N²) comparisons to a tractable candidate set. Matching scores each candidate pair with a similarity measure. Clustering reconciles pairwise decisions into globally consistent entity groups.

Raw records → Blocking → Matching → Clustering → Resolved identity graph

Each stage is independently configurable. The full API:

quickstart.py 
from sandx_er import EntityResolver
import pandas as pd

records = pd.DataFrame({
    "name":  ["Acme Corp", "ACME Corporation", "GlobalTech Inc", "Global Tech"],
    "city":  ["Boston",    "Boston",           "New York",      "New York"],
})

er = EntityResolver(
    blocking="lsh",       # MinHash LSH candidate generation
    similarity="jaccard", # character shingle Jaccard scoring
    threshold=0.4,
)

result = er.resolve(records)

for cluster in result.clusters:
    print(cluster.canonical_id[:8], cluster.record_ids, cluster.confidence)

Blocking strategies

sandx-er ships three blocking methods. LSH (MinHash) hashes each record into a signature and groups candidate pairs by band collision — no key field required, works across all string columns simultaneously. Sorted Neighborhood (SNM) sorts records by a user-specified key field and compares within a sliding window — faster and higher precision when the key is a reliable discriminator. Embedding ANN uses approximate nearest-neighbor search in embedding space via sandx-embed, optimal for semantic similarity.

Matching

The default scorer computes character-level Jaccard similarity across all string fields concatenated into a single document representation. Character shingles (3-grams by default) handle the most common noise patterns — typos, abbreviations, reordered tokens — without requiring field-level alignment. A CosineSimilarityScorer is available for embedding-based matching.

Clustering

Connected components clustering assigns all records reachable through above-threshold similarity edges to the same entity. It is fast and correct when the match graph is clean. Correlation clustering (Kwik-Cluster) runs additional local optimization to break over-merged clusters caused by transitivity errors.

Benchmark 1: Febrl4

Febrl4 is a synthetic person record linkage dataset included in the Python recordlinkage package. 5,000 records per table, 5,000 true 1:1 matches, with realistic noise: typos, transpositions, and missing field values. It is a standard baseline for single-attribute linkage tasks.

terminal 
pip install sandx-er recordlinkage
python -m benchmarks.febrl4
Config Precision Recall F1 Time
LSH + Jaccard · threshold=0.3 1.000 0.955 0.977 1.1s
SNM (surname) + Jaccard · threshold=0.3 1.000 0.384 0.555 0.4s

LSH achieves near-perfect F1 (0.977) because Febrl4 noise is field-level — corrupted surnames, swapped birth dates — and LSH operates across all fields simultaneously, finding matches even when any single field is corrupted. SNM with surname as the sort key achieves perfect precision but low recall: noisy surnames break the neighborhood window.

LSH generalizes across field-level noise; SNM requires a stable discriminating key.

Benchmark 2: DBLP-ACM

DBLP-ACM is a real-world record linkage benchmark from the Magellan ER collection (Köpcke & Rahm, 2010). 2,616 DBLP publication records linked against 2,294 ACM records — the same academic papers indexed differently by two databases. Fields: title, authors, venue, year. Ground truth: 2,220 matching pairs.

Unlike Febrl4, the noise here is structural: venue names abbreviated differently ("VLDB" vs "Very Large Data Bases"), author name formatting inconsistencies, and title variations between the two indexing systems.

terminal 
python -m benchmarks.dblp_acm --data-path /path/to/dblp_acm.csv
python -m benchmarks.dblp_acm --data-path /path/to/dblp_acm.csv \
    --blocking snm --key-field title
Config Precision Recall F1 Time
LSH + Jaccard · threshold=0.5 0.697 0.925 0.795 0.9s
LSH + Jaccard · threshold=0.7 0.900 0.653 0.757 1.1s
SNM (title) + Jaccard · threshold=0.5 0.899 0.957 0.927 0.3s

SNM with title as the sort key wins convincingly: F1=0.927 in 0.3 seconds. Academic paper titles are stable identifiers — different databases rarely abbreviate or corrupt them — so sorted-neighborhood retrieval finds almost every true match without the false positives that LSH generates at threshold=0.5. LSH at threshold=0.7 recovers precision but at the cost of recall.

SNM beats LSH when the blocking key is stable and domain-specific. Choosing the right blocking strategy is the single highest-leverage decision in an ER pipeline.

What the Numbers Mean

Two benchmarks from different domains tell a consistent story:

  • Blocking strategy dominates. The gap between LSH F1=0.795 and SNM F1=0.927 on DBLP-ACM is larger than any threshold tuning could close. The right blocking method is selected by answering one question: is there a field in the dataset that both sources represent consistently?
  • LSH is the safe default. When no reliable key exists — or when noise may affect any single field — LSH generalizes across all fields and achieves strong recall at the cost of some precision. The Febrl4 result (F1=0.977) shows what it can achieve on a well-matched problem.
  • Sub-second throughput at these scales. 10,000 combined records resolve in under 1.1 seconds on a laptop, including all three pipeline stages. The bottleneck at scale is candidate generation in blocking, not scoring.

Installation

terminal 
pip install sandx-er

For embedding-based blocking and matching (requires sandx-embed):

terminal 
pip install "sandx-er[embed]"

All benchmark scripts are in the benchmarks/ directory of the repo. Results are fully reproducible from public data.

What Is Next

The next benchmark target is Abt-Buy: 1,081 Abt.com product records matched against 1,092 Buy.com records, 1,097 true matches. E-commerce product names are structurally different from academic titles and person records — higher variance in format, more numerical attributes, more abbreviations — making it a useful stress test for the blocking stage.

Longer term, the sandx-er pipeline feeds directly into sandx-graph: resolved entity clusters become nodes in a knowledge graph, and the graph consensus engine propagates confidence scores across neighborhood relationships.
